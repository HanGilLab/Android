# 상세 펼침의 최신 허용 조건과 수명 경계

## 문제와 원인

주차 중 보인 상세 버튼의 로컬 expanded 변경은 부모 Route를 다시 구성한다고 보장하지 않는다. 최신 차량 값이 D여도 조합한 UI가 아직 P일 때 오래된 버튼이 상세를 만들 수 있었다. 화면의 enabled나 부모 gate만으로는 처리 경계를 닫지 못했다.

별도 제어 native는 실제 SessionHistoryRoute/VM/Disclosure에 명시적인 합성 세션과 비관찰 차량 StateFlow를 주입했다. 같은 UI turn에서 live 값만 D로 바꾼 뒤 옛 Ready와 접힘 상태를 확인하고 실제 Semantics OnClick을 실행했다. 제품ad0c1d7acb9ba79e323ef1f2329c11b4f0be364a/계측82677d3317f85c81fe1490f0b2c197a442b8ef29에서 상세 부재 assertion이 실패했다. 실제 DDS 수신 순서를 강제한 재현과 구분한다.

Compose Foundation1.9.4의 기본 semantics action은 mutable clickable node의 현재 onClick을 읽는다. 옛 접근성 action이 새 STARTED 수명이나 source의 callback을 채택하지 않도록 실제 포인터와 semantics에 같은 captured toggle을 연결했다.

Home 준비와 Session 준비/기록의 정상 스트림 완료에서도 비관찰 owner만 지우면 이미 열린 상세에 새로운 UI 상태가 발행되지 않는 경계가 있었다. 완료 gate 전 Loaded+허용을 확인한 뒤 정상 완료시키는 JVM3개가 실제로 Failed 대신 Loaded가 남는 assertion으로 실패했다. 정상 완료만 Failed를 발행하고, 취소는 실패로 바꾸지 않으며 오류는 기존 catch에서 처리한다.

## 구현 범위와 선택

- 필수 canExpand callback으로 기존8개 공유 호출부와 debug 진단1개를 연결한다. 기본 true 우회를 두지 않는다.
- 여는 순간과 content 구성 직전에 최신 P/UX 및 표시 source의 허용 조건을 확인한다. 접기는 언제나 허용하며 거부한 펼침 의도는 폐기한다.
- STARTED마다 새로운 수명 token을 발급하고 STOP/dispose에서 영구 무효화한다. opening guard를 보존해 새로운 source guard로 바꾸지 않는다.
- History는 현재 reader/query/job/epoch, 선택 ID, 표시 generation과 현재 원본을 기존 lock에서 대조한다. Next는 기존 currentReady를 재사용하고 동일 seed 재수신 시 generation 보존 계약을 유지한다.
- Home/Session은 기존 구독의 수신 지점에서 최신 source를 읽기 전용으로 보관한다. 추가 DB 구독/쓰기나 권한을 만들지 않는다. 활성 세션/저장이 있다는 이유로 유효한 최근 종료 기록 읽기를 차단하지 않는다. LOADING/RECOVER의 정적 안내도 보존한다.
- debug 진단은 고정된 저장 기록 선택이 아닌 현재 SDK 상태를 읽으므로 기존 live read 판정과 공유 수명 검사를 사용한다.

부모의 표시 Boolean만 넘기는 대안은 최신 값과 다를 수 있어 제외했다. rememberUpdatedState로 guard를 바꾸는 대안은 옛 action이 새 source를 채택할 수 있어 제외했다. 이 경계는 이미 도착한 SDK/source 값을 확인하며, 전달되지 않은 자료 변경이나 관찰되지 않은 짧은 D/P 전환을 예측하지 않는다. 최종 물리적 차량 동작의 원자적 잠금이나 차량 제어를 제공하지 않는다.

## 실제 변경 전 측정

정확성 수정의 처리 비용을 관찰하기 위한 측정이다. 속도 향상을 목표나 성과로 가정하지 않는다. 별도의 이력 진입 측정이나 JUnit/Gradle 시간은 펼침 성능으로 사용하지 않는다.

기준 제품은 ad0c1d7acb9ba79e323ef1f2329c11b4f0be364a, 고정 계측은82677d3317f85c81fe1490f0b2c197a442b8ef29다. SessionHistoryDisclosureMeasureTest의 같은 방법을 비교에서도 바꾸지 않는다. 실제 설치 APK 해시와 선언 revision을 대조하고 완료 기준 파일을 덮어쓰지 않는다.

조건은 Android14/API34 Pleos 에뮬레이터, JDK17 debug, 실제 SDK P+UX, 글꼴1.0/라이트, 원래 준비1/종료 세션9/관찰15/메모0과 같은 카탈로그다. 원래 수신 순서와 최신 종료 source를 고정한다. 새 Activity의 워밍업5회 이후 본 표본30회를 순서대로 수집하며 매회 Home에서 이력을 새로 열어 접힘으로 초기화한다. 캐시를 지우지 않고 무거운 빌드와 동시에 실행하지 않는다.

타이머 밖에서 실제 SDK/원본/source를 대조하고 이력 진입, history_finished 사전 스크롤과 접힘 확인을 한다. 실제 펼침 버튼 클릭 직전부터 scope 전체가 물리적 viewport 안에 생기고 Compose idle 뒤 다시 확인될 때까지 monotonic ms를 잰다. 클릭 전달/semantics/idle 검사 overhead를 포함한다. 이후 첫 과제의 원문과 개수, 전체 자료, Home 복귀를 타이머 밖에서 확인한다. 앱 내부 프레임/GPU/SDK 처리 시간이나 운전자 반응 속도는 아니다.

원본/조건 불일치, 실제 P/UX 거부,20초 endpoint 미확인, 예외/복원 불일치는 실패로 남기고 중단한다. 느린 표본을 버리거나 누락을0으로 채우지 않는다. 워밍업과 본 표본의 성공/실패/누락/미실행/제외를 분리한다. Q1/Q3는 정렬한 표본의 아래/위 절반 중앙값이다.

## 수정 후 실제 검증과 비교

수정 제품/계측은af0cd94851b49fbfba1d6fe2ea513e2dd5e2f05c다. 측정 소스는 기준82677d3과 바이트 동일하며 별도 이력 진입 계측도 변경하지 않았다. 실제 제품 APK와 instrumentation APK의 각 SHA256을 보고서와 대조했다. 두 단계의 원본 자료, 고정 source, 카탈로그, 환경과 측정 계약은 모두 같았고 기준 완료 파일 해시도 그대로였다. instrumentation APK는 다른 경계 검사가 추가돼 서로 다르며 같은 측정 메서드의 click/endpoint는 보존했다.

JDK17 전체 verify와 debug/native/unsigned release 빌드가 성공했다. 저장JUnit38개 suite/460개 검사 집계에서 실패/오류/건너뜀은0이며 정상 종료 RED3개도 수정 후 통과했다. 변경 없는 Gradle task의 유효 결과 재사용과 실제 변경 모듈 실행은 성능 표본으로 세지 않았다. 동일 Route native1개와 공유 컴포넌트 native5개가 성공했고 skip은0이다. 이6개는 명시적인 합성 입력을 사용한 정확성 검사이며 실제 SDK 성능이나 DDS 경합 재현으로 부르지 않는다.

실제 Pleos 기본 글꼴/라이트1회와 글꼴1.3/다크 재시도1회가 성공했다. debug 진단 열기/SDK 출처/닫기, 원래 종료9개와 각 요약/원문/선택, 재생성/STOP-START, 실제 브라우저 DDS와 앱 SDK의 D 잠금/P 재허용을 확인했다. 최초 확대 실행1회는 D 전환 전 첫 진단 tag20초 미확인으로 실패했다. 실패 당시 저장 화면은 기본 내비가 전면이었고 frontMatchesExpected=false, semanticsRoots0이었다. 전체 원본/권한과 의도한 글꼴/테마 외 설정 보존을 확인한 뒤 실제 한길 전면을 확인하고 같은 APK/제한시간/성공 조건으로 재시도했다. 최초 실패는 통과로 바꾸지 않았다. 이 원인은 이전 실행의 history_finished timeout 미확정 기록과 별개다.

실제 native/측정 이후 모든 원래 테이블/필드/SQLite 저장 타입/순서/시퀀스/권한/설정이 정확히 보존됐고 기준 글꼴/테마와 Home 복귀를 확인했다. 본인이 시작한 AVD와 forwarding만 정리했다. 실제 검증에서 독립 UX 제한/오류/삭제를 주입하거나 Next/Course 전체 수동 흐름을 새로 수행한 것은 아니다. 그 경계는 변경한 VM 검사와 공유 native에 구분해 추적한다. 이번 구현은 새 저장/권한/자료 삭제나 성능 최적화를 추가하지 않는다.
