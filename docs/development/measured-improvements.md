# 변경 전후 측정 기준

개선은 실행한 전후 측정으로 무엇이 얼마나 달라졌는지 설명한다.
테스트가 많이 통과했다는 사실은 정확성의 보조 근거이며 성능 향상의 대체물이 아니다.
현재 README의 네 사례는 정확성과 데이터 보존 사례이며 전후 성능 측정 자료는 없다.

## 변경 전에 정할 것

1. 실제로 관찰한 병목과 사용자 또는 시스템에 미치는 영향을 적는다. 느릴 것 같다는 추측만으로 최적화를 시작하지 않는다.
2. 병목에 직접 연결되는 지표와 단위를 고른다. 화면 반응/프레임 시간, DB 조회/쓰기 지연, 할당량/메모리, I/O나 불필요한 호출량처럼 비교할 대상을 구체화한다.
3. 기준 커밋, 고정 입력/데이터 크기, 빌드 종류, 측정 도구와 실행 조건을 기록한다. 공개 기록에는 기기 식별자나 개인 경로 대신 재현에 필요한 익명 조건만 적는다.
4. 워밍업과 반복 횟수, 전후 실행 순서, 실패/제외 기준을 먼저 정한다. 변경 전 기준값을 실제로 실행해 원값을 보존한 다음 구현한다.

## 같은 조건으로 비교하기

전후에 같은 시나리오, 데이터와 빌드 종류를 사용한다. 네트워크/타일/DB 캐시, 콜드/웜 시작, 글자 크기와 테마 등 지표에 영향을 주는 조건은 통제하거나 별도 표본으로 나눈다.
가능하면 전후 실행 순서를 번갈아 측정해 발열과 실행 순서 영향을 살피고 각 실행의 원값을 남긴다.
워밍업과 실패/누락/제외 표본은 성공 표본과 구분하며 유리한 결과만 골라 평균내지 않는다.
실제 기기와 에뮬레이터, debug와 release 결과를 섞지 않는다. JDK/Gradle 검증은 JDK17로 실행한다.

## 결과에 남길 것

| 항목 | 기록 내용 |
|---|---|
| 대상과 절차 | 기준/비교 커밋, 고정 시나리오와 입력, 재실행 절차 |
| 조건 | 익명 실행 환경, 빌드 종류, 도구, 캐시와 워밍업 조건 |
| 표본 | 반복 횟수와 원값, 성공/실패/누락/제외 수와 이유 |
| 비교 | 전후 원값, 중앙값과 적절한 분포 지표, 절대 차이와 개선율 |
| 한계 | 반복 편차, 회귀 여부, 아직 측정하지 않은 조건 |

작을수록 좋은 지표의 개선율은 `(변경 전 - 변경 후) / 변경 전 × 100`이다.
클수록 좋은 지표는 비교 방향을 먼저 명시한다. 기준값이 0이면 상대 개선율을 계산하지 않고 원값과 절대 차이만 쓴다.
적은 표본의 p95나 평균 하나를 안정적인 대표값으로 단정하지 말고 표본 크기와 분포에 맞는 통계를 고른다.
차이가 측정 잡음 범위이거나 조건이 다르면 개선을 확정하지 않고 한계를 기록한다.

## 검증과 README 반영

측정 전후에 관련 회귀 검증을 실행해 잠금 조건, 데이터 출처, 저장 보존과 실패 동작이 유지되는지 확인한다.
회귀 검증은 계속 실행하고 근거는 작업 계획, PR과 CI에 보존한다. README에는 회귀 검증 근거, 테스트 수/목록과 JUnit/CI 집계 설명을 넣지 않는다.
실제 성능 자료를 확보했을 때만 해당 사례의 결과에 개선 전후 실측 성능, 개선폭과 측정 조건을 추가한다. 회귀 테스트 수, 상태 조합 수와 저장 행 수는 이 성능 수치를 대신하지 않는다.
JUnit 보고서의 시간이나 전체 Gradle/CI 소요 시간을 앱 성능으로 사용하지 않는다. 캐시 재사용 결과를 새로운 측정 표본으로 계산하지 않는다.
가짜 저장소/제어된 시각의 단위 테스트를 실제 SDK 수집 속도나 운전자 효과로 표현하지 않는다.

전후 측정이 확인된 사례가 기존 사례보다 기술 역량과 판단을 더 잘 입증하면 README의 해당 사례를 교체한다.
각 사례는 문제, 원인, 해결, 결과, 대체안/회고, 코드 순서를 지키며 최종 개수는 정확히 4개다.
현재 측정이 없으면 성능 개선율을 만들지 않는다. 측정 계획을 실행 결과로 올리지 않는다.
문서의 배치나 문구만 바꾸는 작업은 앱 실행 성능 개선이 아니므로 적용 제외 이유와 링크/렌더 검증을 남긴다.
