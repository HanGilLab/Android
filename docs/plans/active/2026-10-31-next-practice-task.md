## 목표와 범위

최근 종료 연습의 복습 영역에서 당시 목표/코스와 버전을 다시 확인하고, 사용자가 같은 코스의 다음 과제를 직접 선택해 저장한다. 기존 일반 준비 경로는 유지한다. 기존 SDK/저장소/주차 계약을 사용하는 독립 범위이며 실제 도로 구간 복습, 자동 추천/능력 평가, 새 세션 자동 시작, 위치/내비 API/새 권한/DB 스키마는 추가하지 않는다. APP-06과 APP-07 전체 완료는 별도다.

다음 준비 저장은 별도 domain 계약과 Room 구현으로 최신 종료 source 전체 스냅샷, 활성 세션 부재와 현재 카탈로그를 쓰기 트랜잭션 안에서 확인한다. 아직 Room이 방출하지 않은 새 활성/종료 기록도 저장 경계에서 차단한다. UI는 현재 source를 재조회하고 조회/표시 세대로 옛 조작을 차단한다. 과제를 자동 선택하지 않으며 명시적 선택과 저장 이전에는 기존 준비를 바꾸지 않는다.

## 변경 전후 측정

다음 준비는 새 source 유효성 계약이다. 기존 일반 준비의 저장 API를 기준으로 추가 원자 검증 비용을 측정한다. 빠른 저장이나 사용자 수행 시간 개선을 미리 가정하지 않는다. UI 단계 수, 단위 검사 수나 JUnit/Gradle 시간을 성능으로 사용하지 않는다.

- 가설: 현재 저장 API보다 source/활성/카탈로그 검사를 포함한 원자 저장이 더 많은 DB 작업을 할 수 있다. 실제 비용과 편차를 먼저 확인하고 무결성과 지연의 tradeoff를 판단한다.
- 지표/단위: 실제 제품 Room 저장 API 호출부터 트랜잭션 완료 반환까지 Android monotonic wall time, ms. 같은 고정 next target을 정상 P+UX에서 저장한다. SDK 연결 시간/화면 조작/JUnit 전체 시간/원래 준비 복구 시간은 구간 밖이다. 두 API에 동일한 실제 SDK guard를 전달하며 UI/VM의 draft/reader/action 확인 비용은 이 저장 경계 측정에 포함하지 않는다.
- 기준/비교: 변경 전0838c3c의 기존 PracticeRepository.saveSelection, 변경 후 동일 제품의 변경하지 않은 기존 API와 새 NextPracticeRepository.saveSelection. 제품/계측 commit은 실제 실행 때 기록한다.
- 조건: 같은 Android14/API34 전용 Pleos 에뮬레이터, JDK17 debug, 기존 schema4 준비1/종료9/관찰15/메모0, 같은 최신 종료 source/현재 카탈로그/target task/권한/글꼴1.0/라이트, 실제 SDK P+UX 허용. 가짜 repository/시각/SDK 입력은 쓰지 않는다. 무거운 Gradle과 계측은 순차 실행한다.
- 워밍업/표본: 먼저 기존 API5회 워밍업과30회 측정. 변경 후 두 API 각5회 워밍업 뒤30쌍, 홀수쌍 old→new/짝수쌍 new→old로 교차한다. 각 호출 전 같은 원래 준비로 복원하고 복구/읽기 확인은 측정 밖이다. 앱 프로세스/SQLite 연결은 새로 시작하고 워밍업 후의 warm 조건으로 비교한다. 캐시를 임의로 비우지 않으며 journal/page/자동 checkpoint 조건은 실제 읽어 기록한다.
- 실패/제외: source/target 불일치, P+UX 미허용, 저장 실패/예외/복구 불일치는 실패로 기록하고 중단한다. 임의의 느린 표본 제거/0 대체를 하지 않는다. 성능 구간 누락은 별도 누락이며 성공 표본으로 세지 않는다.

- 한계: debug 에뮬레이터의 해당 저장 경계이며 실제 차량/사용자/전체 화면/SDK 수집 성능이 아니다. 새 경계가 빨라지지 않아도 성능 향상으로 쓰지 않는다. 원문 source/개인 환경/원시 로그는 ignored 근거에만 보존하고 공개에는 정제 수치/조건만 남긴다.
- 재현: 실제 계측 절차는 구현/실행 후 별도 개발 문서에 적는다. 계획은 실행 결과가 아니다.

## README 사례 선정과 비교

기존4사례와 순서를 먼저 보존한다. 새 source 원자 경계가 기존2번의 P+UX/중복/트랜잭션/당시 snapshot보다 어떤 채용 근거에서 더 강해졌는지 실제 결과 확보 후 비교한다. 새 기능/검사 수나 최신성만으로 교체하지 않는다. 성능 미측정 표, 회귀 근거와 집계는 README에 넣지 않는다. 문서/사진 배치는 앱 실행 성능 변경이 아니므로 실제 픽셀/링크/렌더로 검증한다.

## 남은 문제와 인계

제품 연결, 전체 검사, 실제 화면과 교차 측정은 끝났고 최신 PR CI/리뷰/병합은 남아 있다. APP-06 실제 구간 복습/APP-07 전체, MAP-01 원래 리뷰/Empty/독립 UX 조합 등은 별도 미완료다. 다른 저장소/문서와 완료된 이력 정리를 재개하지 않는다.

## 구현과 검증 과정의 실패 구분

초기 Room 검사21개 중4개는 coroutine 디버그 stack trace 복구 wrapper 때문에 예외 객체를 최상단에서 직접 비교하다 실패했다. 이때 뒤쪽 DB 보존 assertion은 미실행이었다. 실제 wrapper의 같은 클래스/메시지/인공 stack frame과 최종 원본 cause 동일성을 확인하도록 검사만 고쳐21개 전체와 보존 assertion을 통과했다. 그 전에 entity의 isActive 접근과 feature fixture의 source 이름 가림으로 발생한 컴파일 실패도 수정했다. 초기 formatter의 긴 줄/if-wrapping과 계측 성공 문자열의 줄바꿈 파싱 실패는 실제 계측 실패나 제품 동작 실패가 아니다. 어느 실패도 성공으로 합산하지 않았다.

## 독립 코드 검토와 사례 비교

독립 읽기 검토에서 Room pre/post 검증과 rollback, 전체 frozen seed 비교, 오류 화면 generation과 leave의 같은 lock 처리, source/선택이 묶인 Saved token 단회 소비를 확인했으며 추가 확정 결함은 없었다. 이는 최신 PR Codex 리뷰를 대신하지 않는다. 새 연결은 기존 사례2의 원자 저장과3의 비동기 세대 경계를 조합한 응용이다. 현재4개를 바꾸면 차량 안전/동시성과 snapshot/네이티브 View 경합/SQLite 자료형 손실의 기술 범위가 줄고 설명이 중복되므로 보존한다. 기준 계측이나 새 API/검사 수만으로 우월성을 주장하지 않는다.

README에는 실제 통과한 기본/확대 다크 앱 영역 사진2개와 구현 기능 설명만 추가했다. 기존4사례/순서/핵심 코드11개는 보존하고 회귀 근거나 미측정 개선율은 넣지 않았다. 새 관찰은 개선이 아닌 무결성 계약의 비용이고 분포/기준 이동 때문에 기존 사례보다 강한 성능 개선 근거가 아니므로 사례 교체 근거가 없다.
