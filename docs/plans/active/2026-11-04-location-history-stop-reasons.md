# 저장된 위치 수집 중단 원인 복습 연결

- 상태: 진행 중, 실제 화면 검증과 최신 PR 병합 조건 미충족
- 요구사항: 출품 체크리스트 APP-06의 저장 기록 복습, APP-04의 누락/거부/미지원/오류 구분

## 목표와 범위

기준 main `a33e74b0d19118ca1652bca804f63a0fb5e3cacb`에는 저장된 위치 실행과 표본을 복습하는 경로가 이미 있다. 그러나 실행 카드가 `stopReason` 12종 중 저장 상한만 별도 표시하고, 나머지는 공통 STOPPED/FAILED/INTERRUPTED 제목으로 묶는다. 사용자는 명시 중지, 전면 이탈, 연습 마침과 권한 거부/SDK/어댑터/저장 오류를 저장 원본대로 구분할 수 없다.

기존 실행 카드에 저장된 중단 원인 한 행을 연결한다. 원인이 없는 OPEN은 미기록으로 표시하고 종료 시각을 추정하지 않는다. 기존 저장 상한 안내와 과거 중단 경고, 상세 잠금과 출처를 보존한다. 새 수집, SDK 호출, 권한 요청, DB/schema 변경, 위치 지도와 실제 도로 구간 연결은 범위에 넣지 않는다. 과거 종료 이력에서 다음 준비로 연결하는 작업은 latest-only 저장 계약까지 변경해야 하므로 별도 범위로 남긴다.

## 완료 조건

- [ ] 저장된 12종 중단 원인이 각각 읽을 수 있는 한국어로 표시된다.
- [ ] 원인 미기록, OPEN, 알 수 없는 끝 시각과 과거 중단 경고를 정상 종료로 추정하지 않는다.
- [ ] 저장 상한 안내, 저장 실행/표본 순서, 전체 source와 token, P+UX 및 RESUMED 경계가 유지된다.
- [ ] 합성 UUID/Room의 제어 UI 검증에서 모든 원인, 원인 없는 OPEN, 원본 보존과 권한/SDK 비호출을 확인한다.
- [ ] 기본 라이트와 1.3배 확대 다크에서 본문 가시성/줄바꿈/버튼 도달과 잠금 복귀를 실제 확인한다.
- [ ] JDK17 전체 verify, 계측 APK 빌드, 최신 head 필수 CI와 Codex 리뷰 및 지적 처리가 완료된다.
- [ ] 실제 병합, main ff-only 동기화와 병합 브랜치 정리를 확인한다.

## 구현 단계

1. 현재 화면, typed 종료 이유, Room 검사와 기존 제어 검증을 읽어 중복 구현을 피한다.
2. 현재 source의 `stopReason`만 표시하며 원인별 명시적 문구와 미기록 문구를 연결한다.
3. 합성 저장 자료의 제어 UI 검증을 추가하고 기존 잠금/오래된 행동 경계를 보존한다.
4. 필요한 자동 검사와 실제 화면 조건을 각각 기록하고 검토한다. 실제 수동 검증이 불가능하면 미실행으로 남기고 병합하지 않는다.

## 변경 전후 측정

- 관찰 근거: `LocationHistoryScreen`이 공통 run.status를 제목에 표시하고 `LIMIT_REACHED`만 별도로 표시하며 나머지 저장 원인은 렌더하지 않는다. 저장 계약에는 12종 모두 존재한다.
- 이번 변경은 저장된 필드의 의미를 제품에 연결하는 기능 추가다. 실행 지연이나 사용 시간 단축의 최적화로 주장하지 않는다. 기존에는 같은 원인 열람 행동이 없어 동일 동작의 전후 성능 비교가 성립하지 않으며 동조건 실측 없이 향상, 동등성 또는 무회귀 수치를 만들지 않는다.
- 기준 커밋: `a33e74b0d19118ca1652bca804f63a0fb5e3cacb`.
- 실제 성능 표본, 중앙값/분포/차이/개선율: 미측정. 테스트 통과 수와 저장 실행 수는 정확성 근거로만 관리한다.
- 이 변경으로 속도나 사용자 성과를 주장하려면 [전후 측정 기준](../../development/measured-improvements.md)에 따라 지표/단위, 동일 입력과 빌드, 콜드/웜 및 캐시 조건, 워밍업/반복/순서, 제외 기준을 먼저 고정하고 별도 기준값부터 측정한다.

## README 사례 비교

저장 원인을 보여 주는 이번 연결은 기존 네 사례의 비동기 소유권, SQLite CAS/rollback, native 입력 경계와 수명주기 복귀 문제보다 강한 원인 규명/실제 측정 근거를 아직 확보하지 못했다. 네 사례의 내용과 순서, 실제 코드와 화면을 보존하고 다섯 번째 사례를 추가하지 않는다. README에 테스트/CI 집계나 미측정 성능 수치를 넣지 않는다.

## 남은 문제와 인계

실제 화면 검증, 리뷰와 병합 전까지 계획은 active로 유지한다. PR83의 별도 삭제 고지 검증, 실제 도로 구간/지도, 과거 종료 이력의 다음 준비, APP-04/APP-06/APP-07 전체 완료를 대신하지 않는다. 기존 위치 동의 소비 원장은 닫힌 상태로 보존하며 추가 권한/SDK/JDI 실행은 없다. 필수 완료 수는 해당 항목의 전체 완료 조건을 충족하기 전 변경하지 않는다.

## 이번 구현과 검토 기록

- 기존 run.status와 다른 저장 중단 원인 한 행을 연결했다. 12종을 exhaustive when으로 처리하며 null은 미기록으로 표시한다. 기존 상한 안내, 출처, 불연속 경고, 끝 시각 미확인과 현재 P+UX/RESUMED/token 검사는 유지했다.
- 독립 검토에서 HOST_STOPPED는 host coroutine 종료뿐이므로 화면 이탈로 단정할 수 없고, ADAPTER_ERROR는 예외 외에 시작 조건 철회/원본 읽기 실패도 포함함을 확인했다. 각각 화면 수집 실행 중단과 앱의 위치 수집 처리 중단으로 정정했다. 저장 enum보다 구체적인 고장 원인은 추정하지 않는다.
- 새 제어 시나리오는 12종 원인과 OPEN 미기록, 실행 이동, D/P와 독립 UX 잠금, 오래된 행동 거부, 저장 snapshot/세션/준비/sequence/FK 보존과 플랫폼 동작 비호출을 검사하도록 작성했다. PROCESS_INTERRUPTED는 다른 합성 process의 OPEN을 실제 Room 복구 API로 회수하며 끝 시각을 만들지 않는다. 마지막 OPEN은 읽는 동안 원형을 유지하고 fixture 정리 때 정확한 소유자로 닫는다.
- 위 시나리오의 실제 실행은 0회다. 기존 visual helper도 manualLocationRecordingVisual=true의 실제 기본/확대 다크 실행 전에는 가시성 검증 근거가 아니다. APK 빌드 성공을 실제 화면/장치 성공으로 바꾸지 않는다.
- JDK17 Spotless, 전체 verify의 품질/모듈 경계/Lint/단위 테스트와 debug/unsigned release, 계측 APK 빌드를 모두 통과했다. 집계한 JUnit XML은 1,132개, 실패/오류/건너뜀 0이며 cache/up-to-date가 포함될 수 있다. 새 UI 계측은 이 JVM 집계에 포함된 실행 성과가 아니다.
- 실제 화면 기본 라이트/1.3 다크와 새 제어 시나리오 실행, 최신 PR 필수 CI/Codex 및 병합은 아직 미완료다. 계획은 active에 남기며 새 권한/SDK/JDI 또는 기기 작업은 0회다.
- README는 현재 main과 바이트 동일하며 정확히 네 사례, 지정 여섯 항목 순서와 기존 코드/실제 이미지를 유지했다. 이 기능 연결을 성능 향상이나 기존 사례보다 강한 채용 사례로 확대하지 않는다.
