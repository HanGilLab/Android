# 고정 시연 지점의 native 탭 선택

- 상태: 제품 구현/최종 검증 완료, 최신 PR 검사와 리뷰 대기
- 요구사항: 비공개 출품 체크리스트 MAP-03의 독립 고정 시연 지점 선택. 실제 도로 구간 선택과 전체 MAP-03은 미완료 유지.

## 목표와 범위

현재 main의 검증된 preview, renderer와 선택 계약을 사용해 지도 위 번호를 직접 누르면 같은 목록 선택, 테두리와 설명을 연결한다. 기존 목록은 접근성 대체 경로로 유지한다. OSM 장소 경계 중심을 도로 구간, 출입구, 현재 위치나 내비 목적지로 바꾸지 않는다. DB, 권한, 위치와 내비 API는 변경하지 않는다.

기준 코드에는 목록 선택만 있다. 설치된 MapLibre 13.5 SDK는 onSingleTapConfirmed 때 현재 listener에 LatLng만 전달하고 입력 downTime이나 소유 세대를 전달하지 않는다. 지연 콜백에서 현재 주차 세대를 읽는 방식은 오래된 탭이 D/P 또는 STOP/START 뒤 새 소유권을 빌릴 수 있다. 승인된 DOWN부터 UP까지 직접 고정하는 짧은 단일 포인터 경계를 검토한다. 실제 조회는 현재 renderer의 지정된 지점 layer에 한정하고, 불명확한 중첩이나 빈 곳은 임의 선택하지 않는다.

## README 사례 선정

기존 네 사례는 fail-closed SDK 상태, 파괴적 저장의 CAS/트랜잭션, reader/renderer/native 입력 수명주기, SQLite 실제 자료형 경계다. 새 기능은 같은 세 번째 소유권 축에 해당한다. 실제 RED/GREEN와 대안 판단이 기존 근거보다 독립적으로 설득력이 높을 때만 해당 사례를 교체한다. 신기능이나 코드량만으로 더 낫다고 판단하지 않으며 최종 검증 후 비교 이유를 갱신한다. README에는 회귀 수/목록과 CI/JUnit 설명을 넣지 않는다.

## 남은 문제와 인계

실제 도로 구간/경로, 내비 목적지, 위치 연속 수집과 MAP-03 전체는 범위 밖의 미완료다. 플랫폼 독립 UX/오류 주입의 기존 차단과 원래 PR8/10 최종 리뷰는 이 작업으로 해결하지 않는다. 기존 AVD/사용자 데이터/권한을 보존한다.

## 구현과 1차 검증 경계

- 제품 변경 전 기준 35회와 별개로 기준 b559 APK hash를 직접 대조했다. 같은 실제 circle hit의 native 탭 양성 시나리오는 선택/ACK 대기 30초에서 예상대로 실패했다. 기존 직접 선택 경로가 없던 사실이며 SDK 결함의 재현이나 탭 성능 비교가 아니다.
- 최초 MapPointHitTestTest의 null 오버로드 컴파일 실패는 명시 JsonObject 타입으로 수정했다. JDK17 전체 verify 4단계와 단위 44 suites 614개(실패/오류/건너뜀 0), debug/unsigned release 및 AndroidTest APK가 통과했다. 가시 범위 판정 정리 뒤 품질을 다시 통과했다. 이후 독립 source 감사로 current native source 목록 검증을 추가해 당시에는 최종 제품의 전체 재검증을 후속으로 남겼다.
- APK 해시 확인을 추가 품질 검사와 겹쳐 시작한 첫 준비는 ADB read 30초 timeout으로 끝났다. 계측은 시작되지 않았고 원래 데이터/권한을 바꾸지 않았다. 순서 오류와 실패를 보존한 뒤 Gradle 종료 후 순차 읽기에서 baseline APK hash를 확인했다. 앱 결함/계측 성공으로 계산하지 않는다.
- 최초 후보 제어 native는 10개 중 8개 통과/2개 실패/건너뜀 0이다. 두 preview의 3점/자식 compass와 출처/STOP/source 교체/바깥과 숨김/pan-pinch/wheel의 해당 통과와 무방출 D/P fresh tap 30초 및 음성 흐름의 실제 current hit 실패를 분리한다. 후자는 어느 호출 단계였는지 기존 로그로 확정할 수 없어 카메라 복원이나 SDK 결함으로 원인을 확정하지 않는다.
- 최종 하네스 보강은 무방출 P 뒤 공개 무동작 key dispatch로 새 허용 세대를 먼저 확인한 후 옛 UP 거부/새 DOWN을 대조하고, 음성 입력을 시작하기 전 같은 실제 current circle hit/metadata/가시 범위 조건을 bounded polling으로 확인한다. 입력 도중 다중 포인터 시작/끝의 즉시 hit와 짧은 시간 조건은 유지한다. 이 보강을 기록할 당시에는 재실행 전이었으며, 제품의 timestamp floor를 약화하지 않았다.
- STOP/START와 같은 preview 과제 교체는 새 View/style 대기로 시간 제한 거부와 소유권 거부가 겹칠 수 있다. 이 실제 시나리오만으로 소유권 하나의 효과를 단독 분리했다고 주장하지 않는다.

최종 source 검사와 strict 하네스의 controlled-native-recheck 10개는 같은 제품 APK에서 모두 통과(실패/건너뜀 0)했다. 초기 2개 실패와 한계를 보존하고 제품의 timestamp floor/SDK 조건은 약화하지 않았다. 이 시점에는 실제 Main/SDK, 최종 전후 계측과 전체 검증/리뷰/CI가 후속이었다. 이후 최종 실행 결과는 아래에 별도로 기록한다.

## 확대 글자 선택 테두리의 실제 화면 결함

- 변경 전에 직접 본 확대 1.3/다크의 원본 map crop에서 선택 3번의 바깥 테두리가 아래 가장자리에 닿아 잘리는 것을 관찰했다. 초기 camera fit 40dp는 기존 본체에는 충분했으나 확대된 selection radius와4px stroke의 바깥 반경을 고려하지 않았다. 실제 light/dark Main 절차 통과가 픽셀 잘림 부재를 대신하지 않았음을 분리한다.
- 구현 전 가설/관찰 기준: native selection layer의 실제 radius+stroke와 current projection을 사용해 네 방향의 최소 화면 clearance(px)를 확인하고 최소 4dp 여유를 요구한다. 이 값은 배치/가시성 정확성 근거이며 앱 성능 개선 수치로 사용하지 않는다. 같은 1.3/다크/원래 preview/초기 camera에서 변경 전 실패와 변경 후 통과를 대조한다.
- font1.0의 기존 40dp fit과 고정 진입 계측 source 6f는 유지한다. 비교 성능은 이미 실제 측정한 기준 35회와 동일 font 1.0/라이트 절차로 최종 제품을 비교한다. 확대 글자 camera 여백 변경은 탭 속도 개선이나 해당 진입계측에 없는 조건의 성능 향상으로 주장하지 않는다.
- 최종 구현은 stroke와 글자 배율을 반영한 padding을 사용하고 같은 native layer 실제 속성/viewport 검사와 두 actual Main 테마, 10개 제어 및 최종 전체 검증를 다시 확인한다. 이 관찰 시점에는 수정 전 근거만 확보했으며 개선 완료로 기록하지 않았다.
- 추가 PNG 색상 분석은 로컬 기본 Python의 Pillow 모듈 부재로 실행되지 않았다. 이미지 수정/설치는 하지 않고 실제 SDK 속성과 projection을 쓰는 native 검사로 전후를 확인한다.

기본 1.0/라이트와 확대 1.3/다크의 원래 preview의 실제 Main 시나리오는 각각 PASS/건너뜀 0이며 20개 PNG와 각 3개 point/3개 lifecycle/list 대체/실제 DDS D-P 완료를 보존했다. 두 테마의 실제 선택 ring/설명을 직접 보았으나 확대 edge 결함을 새로 발견해 당시에는 최종 제품 완료로 처리하지 않았다. 원래 모든 SQLite 값/자료형/순서/sequence와 권한/runtime/font/night/IME/proxy는 이미 일치했으며 당시에는 후속 검증 뒤 복원을 다시 확인할 계획이었다.

집중 actual Main의 수정 전 native clearance는 -1.0267333984375px, 요구4px, 확대 1.3/다크의 현재 rendered geometry 3개로 실제 측정해 실패했다. 이는 화면 외곽 침범의 정확성 근거이며 성능 개선 수치가 아니다. 후보 APK와 계측 원형을 보존했고 이 후보는 6f 기반 작업 브랜치의 미커밋 제품 상태였으므로 측정 전에 존재한 제품 커밋처럼 표시하지 않는다. 성능 비교의 기준 제품은 계속 실제 b559/고정6f다.

후속 padding은 기본 글꼴의 기존 명목 외곽 여백 5stylepx를 유지하는 max(40, 실제 selection radius+stroke+5)를 사용한다. font 1.0은 40dp 그대로, 1.3은 46dp이며 실제 최소 4dp 여유는 같은 native 검사로 확인한다. 모든 양자화/기기의 오차를 수학적으로 보장하거나 사용자가 이후 pan한 상태까지 강제하는 정책은 아니다. 공유 상수를 써 테두리 크기와 padding 산식의 분리를 줄였으며 이 정책을 기록한 당시에는 최종 GREEN이 미실행이었다. 실제 후속 GREEN은 아래 최종 결과에 기록한다.

## 첫 전후 성능 결과와 추가 진단 계획

- 첫 고정 비교 35회도 모두 완료했고 baseline 원형/계약/원본 자료/preview/catalog/environment가 동일했다. 본 표본 30개 기준 중앙값 1759.1112925→2265.866355ms, 차이 +506.7550625ms/+28.8074475254%로 관찰상 느렸다. - 두 IQR은 겹치지 않는다. 새 입력 처리의 기존 진입 비용이 원인인지, 순차 실행/캐시/JIT/발열/OS/네트워크의 변화인지 아직 분리하지 못했다. 향상/인과 저하/동등성/무회귀를 확정하지 않는다.
- 추가 실행 전에 정한 진단: 같은 전용 장치, 원래 데이터와 설정, 동일 지원 6f와 원형 APK를 사용해 baseline-repeat(b559)→comparison-repeat(최종 0786) 한 쌍만 추가한다. 각 5warm+30본 표본/같은 30초 endpoint/동일 조건 검사/유리한 값 제외 없음/실패와 누락 별도 보존이다. 전체 순서는 B1→F1→B2→F2이며 추가 원값과 첫 쌍을 합쳐 숨기거나 첫 쌍을 교체하지 않는다. 추가 결과를 보기 전에 순서와 횟수를 고정했다.
- 완료된 첫 baseline/comparison device cache JSON은 byte hash를 확인하고 이 실행만의 별도 archive 이름으로 이동해 보존한 뒤 같은 고정 경로를 새 쌍에서 사용한다. Tile/DB/코드 캐시나 사용자 데이터를 삭제하지 않으며, .bak/.new sidecar가 있으면 임의 삭제하지 않고 차단한다. 로컬 첫 원형/공개 첫 70행은 변경하지 않고 추가 70행만 별도 stage로 append한다.

- 반복 기준도 동일하게 느려지면 환경/순서 변화 가능성을 추가 근거로 남기고, 최종 제품에서만 차이가 지속되면 앱 경계 비용의 원인을 추가 조사한다. 수치가 유리해질 때까지 반복하거나 낮은 값만 대표로 선택하지 않는다.
