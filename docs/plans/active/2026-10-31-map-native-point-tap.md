# 고정 시연 지점의 native 탭 선택

- 상태: 진행 중
- 요구사항: 비공개 출품 체크리스트 MAP-03의 독립 고정 시연 지점 선택. 실제 도로 구간 선택과 전체 MAP-03은 미완료 유지.

## 목표와 범위

현재 main의 검증된 preview, renderer와 선택 계약을 사용해 지도 위 번호를 직접 누르면 같은 목록 선택, 테두리와 설명을 연결한다. 기존 목록은 접근성 대체 경로로 유지한다. OSM 장소 경계 중심을 도로 구간, 출입구, 현재 위치나 내비 목적지로 바꾸지 않는다. DB, 권한, 위치와 내비 API는 변경하지 않는다.

기준 코드에는 목록 선택만 있다. 설치된 MapLibre13.5 SDK는 onSingleTapConfirmed 때 현재 listener에 LatLng만 전달하고 입력 downTime이나 소유 세대를 전달하지 않는다. 지연 콜백에서 현재 주차 세대를 읽는 방식은 오래된 탭이 D/P 또는 STOP/START 뒤 새 소유권을 빌릴 수 있다. 승인된 DOWN부터 UP까지 직접 고정하는 짧은 단일 포인터 경계를 검토한다. 실제 조회는 현재 renderer의 지정된 지점 layer에 한정하고, 불명확한 중첩이나 빈 곳은 임의 선택하지 않는다.

- [ ] drag, pinch, 긴 누름, 취소, 자식 attribution/compass 조작과 빈 지도 입력을 지점 선택으로 오인하지 않는다.

## 변경 전후 측정

- 관찰/가설: 지도 위 번호는 현재 직접 선택할 수 없다. 새 입력 기능에는 동등한 과거 동작이 없어 탭 선택 속도의 개선율은 계산하지 않는다. 새 native handler가 기존 지도 진입에 미치는 비용만 같은 절차로 관찰한다. 느린 앱이나 SDK 병목이 확인된 것으로 단정하지 않는다.
- 지표/단위: 기존 home_map 클릭 직전부터 현재 native style/source/세 지점/fit camera와 Compose endpoint까지 elapsedRealtimeNanos의 ms. 작을수록 좋으며 동작 수나 테스트 수로 대신하지 않는다.
- 기준 제품: b559c6d3cbe79d63e18b238c97cb44e05b46f0a7. MapOpeningMeasureTest는 저장 namespace만 map-point-tap-entry로 분리해 제품 변경 전에 커밋으로 고정한다. 비교 제품 SHA는 실제 구현 후 기록한다.
- 동일 조건: JDK17.0.21, debug, 전용 Pleos API34, 원래 준비/카탈로그/SQLite 전체 보존, 실제 SDK P와 UX 해제, font1.0/라이트. 각 단계는 새 프로세스/Activity로 시작하고 5회 워밍업 뒤 같은 프로세스의 지도 열기/닫기 30회. 앱 시작과 home 사전 스크롤은 timer 밖이며 지도까지 스크롤, 렌더/타일/native조회와 검사 동기화는 포함된다. JSON/캡처/닫기는 제외한다.
- 순서/캐시: 기준→구현→관련 검증→최종 비교 순차 실행. 캐시 삭제 없이 웜 타일/DB/JIT 상태를 유지하며 네트워크/캐시/발열/OS/순서 영향은 완전히 통제하지 못한다. 인과 향상, 인과 저하나 동등성/무회귀를 작은 차이로 확정하지 않는다.
- 표본/제외: 단계마다 워밍업5개와 본 표본30개 전부 보존. 유효 30초 endpoint와 고정 입력/SDK/데이터 조건을 만족하지 못하면 실패로 기록하고 유리한 표본 제외 없음. 누락/미실행/실패/제외를 별도 집계한다. 실패 재실행이면 이전 원본을 덮어쓰지 않고 모든 회차를 구분한다.

## README 사례 선정

기존 네 사례는 fail-closed SDK 상태, 파괴적 저장의 CAS/트랜잭션, reader/renderer/native 입력 수명주기, SQLite 실제 자료형 경계다. 새 기능은 같은 세 번째 소유권 축에 해당한다. 실제 RED/GREEN와 대안 판단이 기존 근거보다 독립적으로 설득력이 높을 때만 해당 사례를 교체한다. 신기능이나 코드량만으로 더 낫다고 판단하지 않으며 최종 검증 후 비교 이유를 갱신한다. README에는 회귀 수/목록과 CI/JUnit 설명을 넣지 않는다.

## 남은 문제와 인계

실제 도로 구간/경로, 내비 목적지, 위치 연속 수집과 MAP-03 전체는 범위 밖의 미완료다. 플랫폼 독립 UX/오류 주입의 기존 차단과 원래 PR8/10 최종 리뷰는 이 작업으로 해결하지 않는다. 기존 AVD/사용자 데이터/권한을 보존한다.

## 구현과 1차 검증 경계

- 제품 변경 전 기준35회와 별개로 기준 b559 APK hash를 직접 대조했다. 같은 실제 circle hit의 native 탭 양성 시나리오는 선택/ACK 대기30초에서 예상대로 실패했다. 기존 직접 선택 경로가 없던 사실이며 SDK 결함의 재현이나 탭 성능 비교가 아니다.
- 최초 MapPointHitTestTest의 null 오버로드 컴파일 실패는 명시 JsonObject 타입으로 수정했다. JDK17 전체 verify4단계와 단위44 suites614개(실패/오류/건너뜀0), debug/unsigned release 및 AndroidTest APK가 통과했다. 가시 범위 판정 정리 뒤 품질을 다시 통과했다. 이후 독립 source 감사로 current native source 목록 검증을 추가해 최종 제품의 전체 재검증은 후속으로 남긴다.
- APK 해시 확인을 추가 품질 검사와 겹쳐 시작한 첫 준비는 ADB read30초 timeout으로 끝났다. 계측은 시작되지 않았고 원래 데이터/권한을 바꾸지 않았다. 순서 오류와 실패를 보존한 뒤 Gradle 종료 후 순차 읽기에서 baseline APK hash를 확인했다. 앱 결함/계측 성공으로 계산하지 않는다.
- 최초 후보 제어 native는10개 중8개 통과/2개 실패/건너뜀0이다. 두 preview의3점/자식 compass와출처/STOP/source교체/바깥과숨김/pan-pinch/wheel의 해당 통과와 무방출 D/P fresh tap30초 및 음성 흐름의 실제 current hit 실패를 분리한다. 후자는 어느 호출 단계였는지 기존 로그로 확정할 수 없어 카메라 복원이나 SDK 결함으로 원인을 확정하지 않는다.
- 최종 하네스 보강은 무방출 P 뒤 공개 무동작 key dispatch로 새 허용 세대를 먼저 확인한 후 옛 UP 거부/새 DOWN을 대조하고, 음성 입력을 시작하기 전 같은 실제 current circle hit/metadata/가시 범위 조건을 bounded polling으로 확인한다. 입력 도중 다중 포인터 시작/끝의 즉시 hit와 짧은 시간 조건은 유지한다. 결과는 아직 재실행 전이며 제품의 timestamp floor를 약화하지 않았다.
- STOP/START와 같은 preview 과제 교체는 새 View/style 대기로 시간 제한 거부와 소유권 거부가 겹칠 수 있다. 이 실제 시나리오만으로 소유권 하나의 효과를 단독 분리했다고 주장하지 않는다.

최종 source 검사와 strict 하네스의 controlled-native-recheck10개는 같은 제품 APK에서 모두 통과(실패/건너뜀0)했다. 초기2개 실패와 한계를 보존하고 제품의 timestamp floor/SDK 조건은 약화하지 않았다. 실제 Main/SDK와 최종 전후 계측 및 전체/리뷰/CI는 아직 후속이다.

## 확대 글자 선택 테두리의 실제 화면 결함

- 변경 전에 직접 본 확대1.3/다크의 원본 map crop에서 선택3번의 바깥 테두리가 아래 가장자리에 닿아 잘리는 것을 관찰했다. 초기 camera fit40dp는 기존 본체에는 충분했으나 확대된 selection radius와4px stroke의 바깥 반경을 고려하지 않았다. 실제 light/dark Main 절차 통과가 픽셀 잘림 부재를 대신하지 않았음을 분리한다.
- 구현 전 가설/관찰 기준: native selection layer의 실제 radius+stroke와 current projection을 사용해 네 방향의 최소 화면 clearance(px)를 확인하고 최소4dp 여유를 요구한다. 이 값은 배치/가시성 정확성 근거이며 앱 성능 개선 수치로 사용하지 않는다. 같은1.3/다크/원래preview/초기camera에서 변경 전 실패와 변경 후 통과를 대조한다.
- font1.0의 기존40dp fit과 고정 진입 계측 source6f는 유지한다. 비교 성능은 이미 실제 측정한 기준35회와 동일 font1.0/라이트 절차로 최종 제품을 비교한다. 확대 글자 camera 여백 변경은 탭 속도 개선이나 해당 진입계측에 없는 조건의 성능 향상으로 주장하지 않는다.
- 최종 구현은 stroke와 글자 배율을 반영한 padding을 사용하고 같은 native layer 실제속성/viewport 검사와 두 actual Main 테마,10개제어 및 최종전체를 다시 확인한다. 현재는 수정 전 관찰만 확보했으며 개선 완료로 기록하지 않는다.
- 추가 PNG 색상 분석은 로컬 기본 Python의 Pillow 모듈 부재로 실행되지 않았다. 이미지 수정/설치는 하지 않고 실제 SDK 속성과 projection을 쓰는 native 검사로 전후를 확인한다.

기본1.0/라이트와 확대1.3/다크의 원래 preview 실제 Main 시나리오는 각각 PASS/건너뜀0이며 20개 PNG와 각3개point/3개lifecycle/list 대체/실제DDS D-P 완료를 보존했다. 두테마의 실제선택ring/설명을 직접 보았으나 확대edge 결함을 새로 발견해 최종제품완료로 처리하지 않는다. 원래 모든 SQLite 값/자료형/순서/sequence와권한/runtime/font/night/IME/proxy는 이미일치했으며 후속검증뒤 다시복원을확인한다.

집중 actual Main의 수정 전 native clearance는 -1.0267333984375px, 요구4px, 확대1.3/다크의 현재 rendered geometry3개로 실제 측정해 실패했다. 이는 화면 외곽 침범의 정확성 근거이며 성능 개선 수치가 아니다. 후보 APK와 계측 원형을 보존했고 이 후보는6f 기반 작업 브랜치의 미커밋 제품 상태였으므로 측정 전에 존재한 제품 커밋처럼 표시하지 않는다. 성능 비교의 기준 제품은 계속 실제 b559/고정6f다.

후속 padding은 기본 글꼴의 기존 명목 외곽 여백5stylepx를 유지하는 max(40, 실제 selection radius+stroke+5)를 사용한다. font1.0은40dp 그대로,1.3은46dp이며 실제 최소4dp 여유는 같은 native 검사로 확인한다. 모든 양자화/기기의 오차를 수학적으로 보장하거나 사용자가 이후 pan한 상태까지 강제하는 정책은 아니다. 공유 상수를 써 테두리 크기와 padding 산식의 분리를 줄였으며 최종 GREEN은 아직 미실행이다.
