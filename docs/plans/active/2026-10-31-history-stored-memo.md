# 선택한 지난 연습의 저장 메모 열람

- 상태: 로컬 구현/자동 검증 통과, 변경 후 계측과 실제/제어 native 검증 대기
- 요구사항: 출품 체크리스트 APP-06/APP-08의 선택한 과거 종료 기록 읽기 연결. 전체 지도 복습과 과정 완료는 별도 미완료다.

## 목표와 범위

변경 전 이력에서는 과거 기록의 SDK 관찰을 읽을 수 있지만 사용자가 직접 저장한 메모는 홈의 최신 종료 기록에서만 확인할 수 있다. 이미 제공되는 sessionId별 SessionMemoRepository.observe를 사용해 선택한 종료 기록의 메모를 주차 상세로 펼친다. 메모 쓰기/삭제/최신 종료 기록 계약, DB/스키마, 권한과 위치/내비는 바꾸지 않는다. 원문, 사용자 메모 출처와 실제 부재/손상/오류를 구분하고 새로운 메모 편집 기능으로 확대하지 않는다.

## 완료 조건

- [ ] 선택한 전체 세션 snapshot, 부모 reader/query/generation과 STARTED 소유권에 고정해 같은 메모 원문만 읽는다.
- [ ] 접힘/선택 변경/삭제/부모 실패/STOP/주행 거부에서 조회를 정리하고 늦은 결과와 옛 재시도가 다른 기록/새 P 소유권을 빌리지 못한다.
- [ ] null 부재, 잘못된 sessionId/토큰/원문, 오류/독립 취소/정상 stream 종료를 구분하고 terminal 실패는 명시 retry로만 재조회한다. 쓰기/삭제를 호출하지 않는다.
- [ ] JDK17 전체 verify와 변경 JVM/native 경계, 실제 기본 라이트/확대 다크 Main/SDK/Room 및 DDS D-P를 확인한다. 실제 자료, 합성 입력과 검사 소유 기록은 분리하며 원래 자료/권한/설정을 보존한다.
- [ ] 같은 기존 이력 진입의 실제 기준과 비교 원값/분포/실패/제외/한계를 기록한다. 새 메모 열람 자체의 이전 동작이 없음을 구분한다.
- [ ] README의 기존4개와 근거를 비교해 더 강한 근거가 없으면 보존하고 유효한 실제 코드/링크, 기존 브랜드/화면과 정확히4개를 유지한다.
- [ ] 동일 최신 head의 필수 CI/Codex/관련 실기/정책을 확인해 정상 병합하고 실제 head/tree/main ff-only/브랜치 정리 및 Notion readback을 확인한다.

## 구현 단계

1. 현재 main, 최신 명세/기존 계획, 환경과 관련 리뷰/CI 및 공식 제출 안내를 확인한다.
2. 기존 이력 진입 계측에 새 격리 계열만 추가하고 지원 commit을 고정해 제품 변경 전 실제 기준값을 측정한다.
3. 기존 History의 같은 lock과 선택 소유권에 cold memo reader를 연결한다. 별도 sessions 재구독/기본 성공값/최신 editor 계약 변경을 피한다.
4. 동일 조건 비교 측정과 자동/실제/제어 검증을 마치고 새 근거를 비교해 README와 계획/PR/Notion에 결과를 구분한다.

## 변경 전후 측정

- 병목/관찰/가설: 과거 저장 메모로 이어지는 제품 경로가 없다. 앱/SDK 지연 병목을 관찰한 것은 아니며 속도 최적화를 주장하지 않는다. 새 메모 detail은 접힌 동안 읽기를 만들지 않아야 한다. 기존 이력 진입에 더하는 비용만 같은 endpoint로 관찰한다.
- 지표/단위/방향: SessionHistoryOpeningMeasureTest의 home_history click 직전부터 같은 Ready/원문/Compose idle endpoint까지 elapsedRealtimeNanos의 ns와 ms. 클릭 dispatch/검사/동기화를 포함하며 앱 전용 frame/GPU/SDK timer나 운전자 효과가 아니다. 작을수록 짧지만 인과 개선/저하/동등성을 확정하지 않는다.
- 기준 제품: 74be91fbebcbf96fba6f479e45efa453955e0f86. 새 history-memo-entry-v1 계열의 격리 prefix만 추가한 지원 commit을 실제 기준 측정 전에 고정한다. 기존 계열/원값은 덮어쓰지 않는다.
- 조건: JDK17.0.21+9/debug/전용 Pleos API34/font1.0/라이트, 같은 현재 사용자/원래 준비/종료9개/관찰15개/메모0개/카탈로그/실제 SDK P+UX 해제. 각 단계 fresh process/Activity, 같은 프로세스의 이력 열기/닫기5warm+30본 표본. 시작/사전 스크롤/닫기/원형 export/캡처/사후 자료 대조는 timer 밖이다. 실제 수가 다르면 측정을 시작하지 않고 원래 입력을 다시 확인한다.
- 순서/캐시: B1→F1 순차. 데이터/Tile/DB/코드 캐시를 지우지 않는다. APK 교체/ART/profile/JIT/OS/발열/순서/네트워크 영향을 분리하지 못하므로 작은 차이나 겹치는 분포로 성능 향상/인과 저하/동등성/무회귀를 주장하지 않는다.
- 표본/제외: 단계별5warm+30본 표본 모두 보존, 고정20초 endpoint/원문/실제 P+UX/원래 입력 일치 실패는 실패로 기록한다. 누락/미실행/제외와 실패를 구분하고 느린 값 제외 없음. 기준0이면 상대율 없음. raw 정수 ns에서 ms와 중앙값/Q1/Q3/IQR/min/max를 계산한다. Q1/Q3는 하위15/상위15 중앙값이다.
- 보존/재현: 원형/설치hash/개인 환경은 ignored 비공개 자료로만 보존하고 공개에는 timing과 익명 조건만 남긴다. 사용자 메모와 실제 SDK 기록, 시연 코스 출처를 구분한다. 실제 메모 양성 시나리오가 검사 소유 세션/메모를 만들면 성능 비교를 먼저 끝낸 뒤 명시적 소유 기록으로만 추가하고 모든 원래 행/자료형/순서/권한/설정을 보존한다. 새 소유 행과 증가 sequence를 원래 전체 DB 동일로 주장하거나 임의로 sequence/DB를 되돌리지 않는다.

## README 사례 비교

기존4개는 fail-closed 실제 상태, 파괴적 저장 CAS/트랜잭션, reader/renderer/native 입력 소유권, SQLite 물리 자료형 경계를 다룬다. 이번 메모 읽기는 기존1번/3번을 확장한다. 최신성/코드량/검사 수만으로 교체하지 않으며 실제 원인 증거/자료 영향/대안 판단/재현 결과가 더 강할 때만 해당 사례를 교체한다. 결과가 없을 때 계획을 개선 성과로 쓰지 않는다. 최종 선정 이유는 실제 검증 뒤 기록한다.

## 남은 문제와 인계

실제 도로 구간, 위치 연속/내비 전환 수집, 지도 복습, 전체 APP06/APP08와 과거 PR1/8/10 최종 리뷰는 이번 독립 열람의 완료로 대신하지 않는다. 사용자의 계정/권한 동의/서명/발송은 확대하지 않는다. 새 공개 캡처/자리표시자는 만들지 않는다.

## 기준 계측과 로컬 구현 검증

- 제품 변경 전에 지원044ad28에서 원래 준비1/종료9/관찰15/메모0의 모든 자료/물리형식/순서/sequence/권한/설정을 보존하고 실제 DDS D 잠금/P 복귀와 Main 전면을 확인했다. 고정 계열 history-memo-entry-v1의5warm+30본 표본은 모두 완료했으며 실패/누락/제외0이다. 전후 원값/통계의 최종 비교는 변경 후 실제 실행 뒤 기록한다.
- 원래 환경을 복원하고 이번 소유 AVD를 종료한 뒤 제품을 변경했다. 기존 부모 receipt lock/source/reader/query/generation에 cold memo reader를 묶고 token/revision의 정확한 당시 상태만 재시도에 사용한다. 부모 변경/실패/직접 거부와 호스트 이탈은 옛 query를 폐기한다. 실제 null만 부재이며 잘못된 원문/토큰/ID/stream 종료와 오류/독립 취소는 terminal 실패다. 최신 editor/저장/삭제/DB/권한/위치/내비는 변경하지 않았다.
- 초기 자동 서식 단계에서 긴 선언과 여러 문장의 자동 교정 순서 문제로 검사가 중단됐다. 진단 도구 준비 오류도 앱이나 SDK 실패와 분리해 로컬에 보존했다. 규칙 완화/억제 없이 동일 ktlint로 선언을 정리한 뒤 원래 Spotless가 통과했다. 이후 새 JVM35개가 실패/오류/건너뜀0이고 JDK17.0.21+9 전체 verify4단계/46suites689개 실패/오류/건너뜀0, debug/unsigned release와 계측 APK가 통과했다. cache/up-to-date를 포함하며 실행 시간을 앱 성능으로 사용하지 않는다.
- 실제 연속 Kotlin 발췌17개의 현재 소스를 모두 대조하고 바뀐 SessionHistoryViewModel 링크5개만 갱신했다. 기존4사례/코드본문/이미지18개/브랜드/순서는 보존했으며 아직 새 기능의 공개 화면이나 기능 소개를 추가하지 않았다. 근거와 실제 화면 확인 뒤 최종 판단한다.
- 이 기록 시점의 제어 native와 실제 Main/SDK/Room은 미실행이고 변경 후 계측도 미측정이다. 자동 검사나 준비한 시나리오를 실제 성공으로 대신하지 않는다.
