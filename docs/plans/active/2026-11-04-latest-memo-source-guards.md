# 최신 종료 연습 메모의 저장 원본 검증

- 상태: 진행 중
- 요구사항: APP-06의 사용자 메모 보존, QA-01/02의 데이터 경계와 저장 예외
- 기준 main: `d6ef11ab1bf7db31e765f5ca7f237aa7a73e5e2e`

## 목표와 범위

`RoomSessionMemoRepository.mutate`는 최신 종료 연습의 메모를 생성/수정/삭제할 때 원본을 `find(...).session()`으로 즉시 변환한다. 같은 저장소의 이력 메모 쓰기와 차량/위치 기록은 이미 원래 SQLite 자료형과 버전 범위를 검사한다. REAL 시각과 Int 범위 밖 버전, 빈 선택/제목이 정상 원본처럼 변환돼 메모 쓰기나 삭제를 허용하는지 실제 Room/SQLite fixture로 먼저 확인한다.

기준 제품을 유지한 채 검증 소스부터 추가해 실제 RED를 확보한 뒤 기존 원시 저장 검사와 원본 문자열 검증만 같은 transaction 안에서 적용한다. 사용자 기기/DB나 SDK는 읽지 않으며 UI/domain/schema/권한은 변경하지 않는다. 별도 활성 연습 중 최신 종료 메모 쓰기를 허용하는 기존 계약을 유지하고 global active 차단을 추가하지 않는다. PR83/86/87의 실제 화면 검증과 미병합 범위는 이 저장 어댑터 수정의 기술적 선행 조건이 아니다.

## 구현 단계

1. 독립 빈 DB에 같은 원본과 보존 메모를 만든 후 지정한 원본 열 하나만 바꾼다. 숫자는 실제 저장 타입/값을 먼저 확인한다.
2. JDK17로 같은 focused source를 실행해 세 쓰기 동작의 결과와 보존 실패를 기록한다. 컴파일/fixture 실패를 RED로 계산하지 않는다.
3. 확인된 결함만 원시 저장 검사와 빈 원본 검증으로 막고 같은 검증 소스를 다시 실행한다.
4. 기존 메모/이력 메모 회귀, 전체 verify와 최신 리뷰를 확인한다. 실제 SDK나 화면 검증을 대신했다고 기록하지 않는다.

## 변경 전후 측정

저장된 원본을 정상으로 강제 변환해 사용자 메모를 수정/삭제하는 의미 정확성 경계의 수정이다. 실행 속도나 사용 흐름을 최적화하지 않으므로 앱/SDK 성능 전후 측정은 적용하지 않는다. 기준/수정 후 같은 Room/SQLite in-memory fixture와 SDK34 Robolectric의 실제 쓰기 결과 및 원본 보존을 비교한다. 각 숫자 손상은 독립 DB에서 생성/수정/삭제를 각각 실행하며 빈 문자열은 원본 열별로 같은 절차를 반복한다. 쓰기 거부 전후 자료형/원값/행 순서/schema/sequence를 비교하고 별도 정상 메모도 보존한다. 실패/미실행/성공을 구분하며 검사 수와 JUnit/Gradle 시간은 성능 지표가 아니다. 추가 조회 비용은 미측정이고 속도 개선/동등성/무회귀를 주장하지 않는다.

## 남은 문제와 인계

기준 재현 전에는 결함과 수정 성공을 확정하지 않는다. 검증은 합성 fixture를 쓰는 Room/Robolectric과 JVM/build이며 실제 사용자 메모/기기/SDK를 대상으로 하지 않는다. APP-06 전체, 기존 앱 PR의 실제 수동 검증과 필수19/54/선택3개 제외는 별도로 유지한다. 완료 조건 충족 전 계획을 active에 둔다.

## 기준 재현과 최소 수정

첫8개 검증은 손상7개 실패와 권한 선행1개 통과였다. 빈 필드 반복은 최초 goalId 실패 후 나머지를 실행하지 않으므로 전열 재현으로 계산하지 않았다. 독립 검토에 따라 여섯 문자열 열을 별도 검증으로 나누고 CancellationException을 손상 거부로 받지 않도록 재전파했다. 보강한13개를 제품 미변경 상태에서 다시 실행해 손상12개 모두 실제 원시 fixture 검사 뒤 생성/수정 Saved, 삭제 Deleted와 원시 자료 변경으로 실패했음을 확인했다. 컴파일/fixture 오류나 취소를 RED로 계산하지 않았다. 두 원래 실행/XML/소스는 각각 비공개에 보존했다.

확인 뒤 같은 쓰기 transaction에서 존재하는 원본의 기존 SQLite 자료형/버전 범위 검사와 빈 선택/제목 검사를 model 변환 앞/뒤에 적용했다. 없는 원본과 첫 권한 검사, 최신 종료 선택, 버전 충돌과 두 번째 권한 검사, 취소/롤백은 기존 경계를 유지한다. 별도 활성 연습의 전역 차단이나 UI/SDK/schema 변경은 없다. 기준 보강 실행과 바이트 동일한 검증 소스의 수정 후13개가 모두 통과했다. 이후 기존 정책대로 포맷한 최종 소스의 JDK17 전체 verify도4단계 성공/종료0이다. 기존 메모/이력 메모와 새 검증을 포함하며 취소/롤백/별도 활성 연습 계약을 유지했다. 최신 PR 검사/리뷰와 실제 병합은 아직 별도로 확인한다.
